# 坐标核验指导（地图怎么核）

这份文档回答一个问题：**清单上的每个地点，凭什么说它在那个位置。**

坐标是整个交付物里**唯一会把人带错路**的东西。文案写偏了只是不好看，坐标写偏了是实害。

核心原则一句话：

> **坐标只有三种合法来源——查到的、按片区锚定的、没有的。绝不允许第四种：猜的。**

---

## 一、三条通道（按优先级）

| 通道 | 用什么 | 置信度 | 什么时候用 |
|---|---|---|---|
| **A · 腾讯地图连接器**（主） | WorkBuddy 连接器「腾讯地图」的 POI 检索 | 高 | 默认通道。素材只给了店名，需要现查 |
| **B · 腾讯位置服务 REST**（降级） | `apis.map.qq.com` WebService API | 高 | 连接器不可用 / 需要批量脚本化时 |
| **C · 用户自带坐标**（最高） | 地图收藏夹导出、用户手写经纬度 | 最高 | 素材本身就有坐标，**直读，不要再查** |

通道 C 优先：**用户手里的坐标是他自己在地图上标的，比任何反查都准。** 拿到就用，别自作聪明去「校正」——那是把准的改歪。

---

## 二、通道 A：WorkBuddy 连接器「腾讯地图」

### 2.1 一次性配置（用户侧）

1. 连接器管理 → 搜索「**腾讯地图**」→ 安装
2. 填入**腾讯位置服务开发者 Key**（连接器字段名 `TENCENT_MAP_KEY`）
   - 申请入口：腾讯位置服务控制台 → 注册 → 创建应用 → 添加 Key
3. Key 只存在本机 `~/.workbuddy` 下，不走外网

连接器底层的接入地址形如（**Key 已脱敏**）：

```
https://mcp.map.qq.com/sse?key=${TENCENT_MAP_KEY}&format=0
```

> ⚠️ **`${TENCENT_MAP_KEY}` 是占位符，不是真值。** 真实 Key 任何时候都不允许出现在脚本、文档、聊天记录、Git 提交里。文档、截图、示例代码一律只写占位符。

### 2.2 会话里怎么用

连接器装上之后，会话中会暴露一组位置服务工具，核验坐标主要用第一个：

| 工具 | 用途 | 本项目用不用 |
|---|---|---|
| `placeSuggestion` | **地点搜索建议 / POI 检索** | ✅ 主要用它 |
| `geocoder` | 地址 → 坐标（正解析） | 只在「素材给的是详细地址」时用 |
| `direction` | 路线规划 | 不用（本页只算直线距离） |

> 工具的实际名称以**当前会话加载到的为准**。不确定就先搜一下有哪些可用工具，别凭记忆硬调。

**调用形态（示意，Key 由连接器内部注入，不需要手写）：**

```
placeSuggestion(
    keyword = "马豫兴桶子鸡",
    region  = "开封市"          # ← 关键参数，见下方陷阱
)
```

**返回怎么读**，逐条比对四个字段：

| 返回字段 | 看什么 |
|---|---|
| `title` | 与素材里的**原称**是否对得上（含分店后缀） |
| `address` | 是否落在素材语境的片区（如「东大寺门食品街」） |
| `location.lat` / `location.lng` | 坐标本体，直接落 `lat`/`lng` |
| `category` / `type` | 交叉印证类别（餐饮/酒店/景点） |

**开封实例（真实检索结果）：**

```
keyword = "马豫兴桶子鸡"  region = "开封市"
→ 命中「马豫兴桶子鸡总店」
   lat 34.793407   lng 114.356431
```

素材原话里是**两家合记**（马豫兴 + 存花），而只查到了马豫兴一家。正确做法是
**不硬凑第二组坐标**，把两家合并成一条并在备注里写明来龙去脉：

```json
"rm": "网友提示：桶子鸡偏咸，宜配浓茶或烈酒 ｜ ⚠ 本条为两家合记（马豫兴桶子鸡 + 存花桶子鸡） ｜ 腾讯地图：马豫兴桶子鸡总店（存花桶子鸡未单独检索到）"
```

注意这条 `rm` 里同时有三种信息：**网友原话**（带 ⚠ 与素材语气）、**合记说明**（防误读成一家）、
**检索证据**（可复核）。这就是一条合格的备注。

**把证据写进 `rm`，让每一条坐标都可追溯**——它是「可复核」与「不可复核」的分界线。
没有证据的坐标，三个月后没人能判断它对不对。

## 三、通道 B：腾讯位置服务 REST（降级 / 批量）

连接器用不了时，直接走 WebService API。**Key 从环境变量读，不写进代码。**

```bash
# Key 放环境变量，别写进脚本
export TENCENT_MAP_KEY="<你的腾讯位置服务 Key>"
```

```python
import os, json, urllib.parse, urllib.request

KEY = os.environ["TENCENT_MAP_KEY"]          # ← 只从环境变量取
BASE = "https://apis.map.qq.com/ws/place/v1/suggestion"

def lookup(keyword: str, region: str) -> list:
    q = urllib.parse.urlencode({
        "key": KEY,                # 注意：只在内存里拼，不落盘、不打印
        "keyword": keyword,
        "region": region,          # 如 "开封市"
        "region_fix": 1,           # 限定在本区域内检索
        "page_size": 10,
    })
    with urllib.request.urlopen(f"{BASE}?{q}", timeout=10) as r:
        return json.load(r).get("data", [])
```

使用要点：

- Key 必须是**「WebServiceAPI」类型**，并在控制台开启该接口的配额；浏览器端 Key（JS API）调不通这个接口。
- `region_fix=1` 是防串城的必要条件（见下方陷阱 1）。
- **不要在日志、报错、截图里输出含 Key 的 URL**——出问题时先摘掉 `key=` 参数再贴。

## 四、三档判定：查到什么，就写什么

检索完每条只有三种结局，**没有第四种**：

| 结局 | 判据 | 落字段 | 页面表现 |
|---|---|---|---|
| **精确** | 检索结果里**指认得出就是它** | `lat`/`lng`，`loc` 省略或 `"exact"` | 实心圆点 |
| **区域近似** | 无独立 POI：夜市摊、园内摊、已改名、品类名 | **所属片区锚点坐标** + `"loc":"approx"` | 空心虚线点 + 「区域近似」 |
| **未定位** | 检索不到唯一匹配 | **不写** `lat`/`lng` | 卡片标「未定位」，不出点 |

判据是「**能不能在检索结果里认出它**」，不是「我猜它大概在哪」。

区域近似的正确做法：取片区锚点（如「书店街」「鼓楼夜市」的坐标），加**确定性微偏移**避免点完全重叠（偏移量由 id 推导，不用随机数——随机数会让每次构建结果不同，无法比对）。

```python
dy = ((i * 37) % 100 / 100 - 0.5) * 0.0018   # ≈ ±100m，由 id 决定
dx = ((i * 53) % 100 / 100 - 0.5) * 0.0022
```

同时把 `ad` 写成「XX 一带（无独立 POI）」，**页面和地址自洽**。

## 五、逐条核验流程（七步）

1. **建清单**：识别完素材，先出一张「名称 / 类别 / 区域 / 素材原话」表，**不急着查坐标**。
2. **判类型**：逐条标「应该有独立 POI / 不可能有 POI」——夜市摊、园内摊直接进区域近似，不用浪费检索。
3. **批量检索**：对「应该有 POI」的逐条检索，一次一条，**不合并查询**（合并会丢精度）。
4. **比对**：名称、片区、类别三项都对得上，才落精确坐标；有一项存疑 → 降级或留两条待确认。
5. **记证据**：命中的写入 `rm`（「腾讯地图：XX店」），未命中的也写明（「未单独检索到」）。
6. **机器复核**：跑构建期断言（坐标成对、范围合法、口径闭合）+ 回归探针（圆点数＝可标注数）。
7. **人工抽查**：随机抽 3–5 条，点开详情，**用页面上的导航链接真打开一次**，看落点对不对。

第 7 步不能省。机器只能验「坐标格式对不对」，验不了「位置对不对」。

## 六、高频陷阱（都踩过）

1. **不设 `region` 会串城** —— 「老白汤馆」全国重名几十家，不锁城市会返回外地的。`region="开封市"` 或 `region_fix=1` 必加。
2. **同品牌多分店** —— 取与素材语境最匹配的那家，并**在 `rm` 里注明是哪个分店**。不要默认取「总店」。
3. **同名不同家** —— 宁可留两条并标「待确认」，也不要合并成一个假实体。
4. **平台自身有重复 POI** —— 「总店 / 分店」会同时出现；按地址与坐标邻近判断，别当成两家收录。
5. **已歇业 / 已改名** —— 检索不到就是检索不到，降级为区域近似，**不要拿旧址坐标充精确**。
6. **夜市摊、园内摊没有门牌** —— 本来就不该有精确坐标。给个准的锚点 + 「区域近似」标签，比给个假门牌诚实得多。
7. **坐标系必须一致** —— 腾讯 / 高德 POI 是 **GCJ-02**，与高德瓦片天然对齐。若素材来自 GPS 设备（WGS-84）或国外地图（WGS-84），**必须先做坐标转换**，否则整张图会稳定偏移几百米。
8. **Key 泄露** —— 不要写进脚本、不要跟着 `data.json` 提交、不要贴进聊天。一旦进了 Git 历史，删掉文件也回收不回来，只能去控制台**重新生成 Key**。
9. **不要让 Key 进入交付物** —— `index.html` 里的地图用的是**高德瓦片（无需 Key）**；导航链接用的是腾讯 URI 接口（`referer` 参数，不是开发者 Key）。**交付物里不应该出现任何 Key**。

## 七、交付时怎么向用户交代

坐标这件事必须**明说**，不能含糊：

- 精确 / 区域近似 / 未定位**各多少条**，如实报数；
- 「区域近似」的含义讲清：按片区规划路线，**到附近再问人**；
- 未定位的：知道有这么个地方，**别指望导航**；
- 抽查结果：抽了哪几条、导航链接能不能打开。

模板话术：

> 共 217 条：精确 113、区域近似 70、未定位 34。带坐标的都能直接导航；标「区域近似」的是夜市摊这类没有独立门牌的，按片区走、到附近问一下；标「未定位」的是我没能在地图上认出来的，我没给坐标——宁可不给，也不想把你导到错地方。

**「宁可不给」这句话必须说出口。** 它是这份交付物的诚信底线，也是用户判断可信度的依据。
