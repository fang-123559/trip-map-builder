# data.json 字段规范

`data.json` 是一个数组，每个元素是一处地点。**它是唯一数据源**——页面、统计、地图全部由它派生，不存在第二份数据。

```json
[
  {
    "id": 1,
    "n": "东京食坊（园内美食街）",
    "ty": "园内小吃",
    "ar": "清园内",
    "ad": "清明上河园内东京食坊",
    "ds": "孙记鸡血粉丝汤、炒凉粉、灌汤包",
    "rm": "园内小食街风格，适合边逛边吃",
    "src": "图 16/26",
    "lat": 34.812345,
    "lng": 114.345678,
    "loc": "exact",
    "img": "图片素材/原图/16.jpg"
  }
]
```

---

## 字段表

| 字段 | 必填 | 类型 | 说明 |
|---|---|---|---|
| `id` | ✅ | int | **唯一**、整数。卡片与地图图层靠它关联，重号会串条。建议 1 起递增。 |
| `n` | ✅ | str | 名称。用**素材里的原称**，不要自行润色成品牌全称。合记两家时写「A / B」。 |
| `ty` | ✅ | str | 类型。**必须在 `trip.json` 的 `categoryGroups` 里被显式收录**，否则构建中止。 |
| `ar` | ✅ | str | 区域。用于筛选与卡片标签。建议用「片区」粒度（如 `鼓楼书店街`），不要写完整地址。 |
| `ad` | 否 | str | 地址。查不到就留空或写区域级描述，**不要编**。⭐ 住处条目：**自己看写全（含门牌也行）**；若页面会对外发布，降到路段级（见 `SKILL.md` 第六节） |
| `ds` | 否 | str | 推荐菜/特色。素材里明确提到的才写。 |
| `rm` | 否 | str | 点评/备注。区分「网友说的」与「你判断的」，前者建议保留原话风格。 |
| `src` | 否 | str | 来源。截图类写图号（`图 16/26`）；口述/清单类写「行程主人提供」。**不要写真实姓名**——对外发布时尤其如此。 |
| `lat` | 否 | float | 纬度。**必须与 `lng` 同时存在**，构建期强校验。 |
| `lng` | 否 | float | 经度。同上。 |
| `loc` | 否 | str | 坐标精度档：省略或 `"exact"` = 精确；`"approx"` = 区域近似。**其他值一律报错**。 |
| `img` | 否 | str | 来源截图相对路径（相对输出 html 所在目录）。文件必须真实存在，构建期强校验。 |
| `star` | 否 | bool | 唯一星标（住处/集合点）。**全表最多一条**，构建期强校验。⭐ **默认照实标**（店名 + 地址 + 坐标），它是距离基准与唯一锚点；**仅在该页面会对外发布时**才处理地址与个人称呼，**坐标本身保留**。 |
| `offmap` | 否 | bool | 为 `true` 则**不出现在地图上**，但保留在清单里。用于「素材提到但这次不去」的地点。 |

---

## 坐标三档：怎么选

| 情况 | 怎么写 | 页面表现 |
|---|---|---|
| 地图检索到唯一 POI | 写 `lat`/`lng`，`loc` 省略或 `"exact"` | 实心圆点（颜色＝类别色） |
| 无独立 POI（夜市摊、园内摊、已改名） | 写**所属片区的锚点坐标** + `"loc":"approx"` | 空心虚线圆点 + 「区域近似」标签 |
| 检索不到唯一匹配 | **不写** `lat`/`lng` | 卡片标「未定位」，地图不出点 |
| 素材提到但这次不去 | `"offmap": true` | 卡片标「不在地图标注」，地图不出点 |

**判据是「能不能在检索结果中指认出它」，不是「我猜它大概在哪」。**

宁可标「区域近似」，也不要写一个看起来精确、实际是估的坐标——用户会照着导航，走错就是实害。

## 统计口径（页面统计栏由这些规则自动算出）

```
条目总数 = 全部条目
精确定位 = 有 lat 且 loc≠"approx" 且非 offmap
区域近似 = loc=="approx"
未定位   = 无 lat
（不标注 = offmap，仅在存在时显示）
```

四档互斥且并集为全集，构建期会校验账目闭合。

## 命名约定（强烈建议遵守）

1. **`n` 用素材原称**。「某记包子」不要写成「某记（开封鼓楼店）正宗灌汤包」——多出来的部分是你的主观补充，不是来源事实。
2. **合记写成一个条目**。`ts`/`rm` 里说明是两家合记，这样引用与去重都简单。
3. **同名不同家要拆条并标注**。宁可留两条加「待确认」，也不要合并成一个假实体。
4. **`rm` 里的错别字**：评论区口语内容会有个别错字或歧义，**无法从素材确证的字词不要纳入**，避免以讹传讹。

---

## 去重规则（建议跑一遍）

同一家店常被抓两次：一次是泛称（「黄家老店」），一次是具体分店（「黄家老店(龙亭店)」）。三重检测：

1. **名称归一化**：去掉括号内容、去掉「(XX店)」后缀、统一全半角。
2. **坐标邻近**：已有坐标的两条距离 < 200m 视为同一实体。
3. **名称互包含**：一条的名称完整包含另一条。

三条中命中任意两条，才合并——只用名称会导致误合并（不同分店确实同名）。

## 规模参考

| 规模 | 条目数 | 说明 |
|---|---|---|
| 小型 | < 50 | 一次短途游，手工整理完全够 |
| 中型 | 50–250 | 本项目样例（开封 217 条），需要去重与口径核对 |
| 大型 | > 250 | 建议先按片区拆成多份 data，避免单页过重 |

条目数不影响构建速度（纯 JSON 内联），但**影响验证成本**——每条坐标都该有人工可追溯的来源。
